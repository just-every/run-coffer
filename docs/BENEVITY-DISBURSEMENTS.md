# Reviewed Benevity disbursements

The owner or an admin opens **Payouts → Review donor matches → Upload a Benevity disbursement**. This is a local uploaded-file door; it establishes no provider connection, account authority, live qualification or RER Managed integration availability.

Upload a UTF-8 CSV with unique headings, at most 150 KB and 100 contributions from one source organization and disbursement. Map the actual report columns to organization, disbursement, transaction and donor identities; donor name and email; contribution date; explicit USD currency; gross contribution, actual fees and net payout; fund and campaign provenance. Supply independent report or deposit controls for gross, fees, net and deposit date. Amounts are dollar decimals, not floating-point cents. Zero actual fees are supported; an absent fee is unknown and holds the upload. Gross less actual fees must equal net on every row and the complete batch.

Map each source fund and campaign label explicitly to an existing native destination. A source reporting no campaign uses the explicit value `none`. Missing provenance remains held. Coffer retains the original labels and the reviewed translation; it never assigns a giving form based on a fund or campaign.

Source acknowledgment status may be `acknowledged`, `not acknowledged`, `do not acknowledge` or `unknown`. Missing status remains unknown. An optional supplied date and method remain source facts. No date, communication consent, donor fee-cover agreement or acknowledgment evidence is invented. The full gross contribution is the receipt amount; actual fees reduce the deposit rather than the donor's contribution. Goods or services initially remain unknown and require the ordinary human classification before receipt preparation and approval. Upload and batch approval send no receipt.

Preview writes private review evidence only. Every source appears in the existing donor-match queue, qualified as Benevity rather than a Stripe charge. Select a current donor from the email candidates, explicitly confirming the source identity. Shared email never chooses a person automatically; missing candidates wait for corrected native contact records and a fresh selection. Selection writes no gift, fee or payout.

After every source has a current selection, approve the exact batch version and fingerprint. The transaction rechecks current authority, each selector's active role and version, canonical donor identities and versions, source facts, source controls and fund and campaign mapping. It atomically records the gross gifts, actual-fee entries and exact payout membership once. Existing native gift storage marks reviewed entry as manual and retains the explicit Benevity provider in source metadata. No synthetic Stripe customer, charge or balance transaction is created. Read the reconciled payout and the existing processing-fee report to compare gross, fees, net, funds, campaigns and the explicitly absent giving form.

An identical file and interpretation return the original review. Concurrent approval cannot create duplicate money. Changed disbursements, conflicting transaction identities, repeated rows, unsupported currencies, refunds, negative amounts and incomplete money remain refused or held. Correct an incomplete source before uploading a new review; this door does not replace or amend recorded disbursements. It creates no schedules, replacement plans, provider charges or automatic ingestion.

Files, row evidence and matching candidates are private to current owner or admin review. They are excluded from donor data files. Archives retain the evidence, but a restored installation cannot reuse the old installation's authority to approve pending money. Gifts follow native donor merge and undo; stale pending selections must be reviewed again. Donor erasure removes complete affected source files, row evidence and private matching facts while retaining anonymous amounts and opaque source tombstones. Source donor suppression also prevents a changed-email replay from reviving an erased identity.

The public API follows the native flow under `./src/coffer/payments/platforms/http.ts`: read columns, supply a column mapping and explicit source-value translations, preview, select donors through the existing donor-match endpoint, then approve the exact batch. The integration and browser journey is registered in `./tests/payments.test.mjs` and runs without a provider key or network fake.

Givebutter ingestion and changed transactions, Donorbox, PayPal Giving Fund, other workplace formats, automatic ingestion and changed or refunded disbursement handling remain owed. Wider TEAM-001 authority and all prior provider, policy and prerequisite holds remain unchanged.
